# Read-only source collection

Prefer configured Zotero MCP tools: discover `library_search`, `library_read` and `paper_read` schemas at runtime. Search with explicit `entity=items`, `mode=search`, inspect all candidate metadata and pagination. Read parent metadata, notes, attachments, annotations and related links; read the selected paper's outline and relevant sections or pages and inspect figures visually. API scope may be a chat context or selected library; it does not prove the Zotero UI selection. Use explicit IDs when possible. Search can be broad: compare full title and DOI, not ranking. If two remain plausible ask the user to choose. If a tool is unavailable, ask for a local PDF/export; do not copy a live SQLite database or open it with unsafe immutable flags.

For a Zotero item URI or link, extract the library context and item key and resolve the key in that library; do not treat the entire URL as a title. For an attachment, resolve its parent before collecting sibling notes and files. If the connector cannot resolve a key or library, request the minimum identifier or local PDF needed; do not guess from a similarly named item. Search pagination and scope must be complete before declaring a unique match.

`scripts/inspect_environment.py` reports candidate data and MinerU directories, an installed Zotero version when discoverable, available Python modules and a PowerPoint candidate without opening a Zotero database. It accepts `--data-dir`, `--profile-root`, `--app-dir` and `--mineru-root`; candidates need confirmation through the running Zotero interface. It does not detect every installation, linked attachment, version, or available MCP tool. Check the runtime's actual tools and Zotero's own information rather than interpreting an absent candidate as absence of Zotero.

Discover the configured data directory and linked attachments via Zotero's own interface/preferences or returned paths. Never move source files. Check attached Markdown/HTML/JSON and existing MinerU caches using known attachment identifiers and configured roots; some plugins use numeric attachment IDs rather than parent keys. Do not equate a nearby cache with the paper without metadata/identity evidence. Inspect Markdown relative paths relative to its own directory; retain image, table and structured JSON references, but do not assume a specific version's schema. Compare PDF pages to detect omissions and OCR errors. No automatic model downloads or batch parsing. When needed, use available PDF text/visual extraction locally.

When useful, `scripts/collect_sources.py resolve` checks exact candidates from an MCP search JSON, and `mineru` inspects an explicitly located cache and its `_llm_source.json` identity. See `--help`; a limited search, ambiguous title, missing identity, or identity conflict is never proof of a unique match. Cache output may contain image references only in `content_list.json`, not in Markdown. The helper understands common `img_path` and zero-based `page_idx`, but does not establish that other versions have the same schema or that any extraction is correct. Verify the original PDF and inspect missing image paths.

Maintain an internal representation described in [evidence-schema.md](evidence-schema.md), with paper_metadata, pdf_source, mineru_content, zotero_notes, annotations, figures, equations, references and claims. Each entry should identify its origin, locator, confidence and role (author, user note or interpretation). User notes are leads, not proof. If access is limited, record the actual coverage and request missing information only when necessary.

For a local PDF with no usable parsing cache, `scripts/inspect_pdf.py INPUT.pdf --text-dir OUTPUT_DIR` writes page-numbered text only to the chosen output directory and reports metadata and page coverage. It needs PyMuPDF. Text extraction alone cannot establish formula, table or image fidelity; inspect original PDF pages before relying on it, and report unreadable/scanned pages rather than silently inventing content.
